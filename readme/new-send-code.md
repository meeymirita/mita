# Верификация email: код в Go, хранение в Redis

Цель: перенести генерацию кода подтверждения из Laravel в Go-сервис, хранить код в Redis. Снизить нагрузку на БД и приблизить архитектуру к типичной для крупных сервисов.

---

## 1. Как сейчас vs как лучше

### Текущая схема (код в Laravel)

**Что происходит:**
- Laravel генерирует код → сохраняет хэш и срок в таблицу `users` → рендерит HTML письма (blade) → кладёт в RabbitMQ: `email`, `user_id`, `code`, `subject`, готовый `html`.
- Go только читает сообщение и отправляет письмо через SMTP.

**Минусы:**
- Каждая отправка кода = запись в БД (UPDATE users).
- Код и готовый HTML летят по очереди — лишние данные, при утечке логов/очереди код виден.
- Генерация и доставка размазаны: Laravel знает код, Go — нет.

**Плюсы:**
- Всё в одном месте (Laravel + БД), проще отлаживать «кто что сгенерировал».
- Проверка кода уже есть в Laravel (по БД).

---

### Целевая схема (код в Go, Redis)

**Что происходит:**
- Laravel в очередь кладёт только «кому и зачем»: `email`, `user_id`, `type` (без кода и без HTML).
- Go: забирает сообщение → генерирует код → пишет в Redis → рендерит письмо → отправляет.
- Laravel при проверке кода читает значение из Redis и сравнивает с вводом пользователя.

**Плюсы:**
- Нет записи кодов в основную БД — нагрузка на MySQL/Postgres падает.
- Redis быстрее и дешевле для короткоживущих данных (TTL 5 мин).
- Код не передаётся по очереди и не хранится в БД — меньше поверхность утечки.
- Чёткое разделение: Laravel = бизнес-логика и проверка, Go = генерация и доставка.

**Минусы:**
- Нужен общий Redis для Laravel и Go.
- Проверку кода в Laravel нужно переписать: читать из Redis вместо БД.
- Шаблон письма придётся перенести в Go (или упростить).

---

## 2. Шаг 1: Сообщение в очереди — только «кому и зачем»

### Что менять

В RabbitMQ должно уходить минимальное сообщение, без кода и без HTML.

**Пример тела сообщения:**
```json
{
  "email": "user@example.com",
  "user_id": 123,
  "type": "email_verification"
}
```

### Как

- В Laravel в сервисе/контроллере при «отправить код» больше **не вызывать** `$user->generateVerificationCode()`.
- Не делать `UPDATE users` с `verification_code` и `verification_code_expires_at`.
- В `SendUserCodeRabbitPublisher` убрать генерацию кода и рендер blade; только собрать `email`, `user_id`, `type` и отправить JSON в ту же очередь (например `emails_queue`).

### Зачем и почему

- Очередь не должна быть носителем секрета (код). Меньше данных — меньше риск при утечке и проще контракт между сервисами.
- `type` даёт возможность в будущем одной очередью пользоваться для разных сценариев (верификация, 2FA, сброс пароля и т.д.), если понадобится.

## 3. Шаг 2: Go — генерация кода, Redis, отправка

### Что делать

1. Читать из очереди поля: `email`, `user_id`, `type`.
2. Сгенерировать код в Go (6 цифр), желательно через `crypto/rand`, не `math/rand` — чтобы код был криптографически стойким.
3. Записать в Redis: ключ `verification_code:{user_id}`, значение — сам код (строка), TTL 5 минут (300 секунд).
4. Сформировать тело письма в Go (HTML-шаблон с подстановкой кода).
5. Отправить письмо как сейчас (SMTP).

### Как (технически)

- **Генерация кода:** цикл по 6 раз: `crypto/rand` → цифра 0–9, собрать строку. Либо срез из набора цифр.
- **Redis:** клиент в Go (например `github.com/redis/go-redis/v9`). `SET verification_code:123 "456789" EX 300`.
- **Шаблон:** один `.gohtml` или константа с HTML, куда подставляется код (и при необходимости URL фронта/картинок из конфига или env).

### Зачем и почему

- Код живёт только в Go и Redis; Laravel его не видит до момента проверки (читает из Redis).
- TTL в Redis сам сносит код через 5 минут — не нужны отдельные джобы очистки в БД.
- Шаблон в Go — чтобы из Laravel в очередь вообще не уходил HTML и код; один сервис полностью владеет «родил код → сохранил → отправил».

---

## 4. Шаг 3: Проверка кода в Laravel — читать из Redis

### Что менять

Сейчас проверка идёт по БД: `verification_code` (хэш), `verification_code_expires_at`, `Hash::check($code, $user->verification_code)`.

После переноса код лежит только в Redis. Проверка должна быть такой:

1. По `user_id` прочитать из Redis ключ `verification_code:{user_id}`.
2. Сравнить значение с тем, что ввёл пользователь (строгое сравнение строк, без лишних пробелов/регистра — код цифровой).
3. Если совпало: пометить email верифицированным (`markEmailAsVerified()`), при желании удалить ключ из Redis (`DEL verification_code:{user_id}`), чтобы один код нельзя было использовать дважды.
4. Если не совпало или ключа нет (истёк TTL): вернуть ошибку «Неверный или устаревший код».

### Зачем и почему

- Единственный источник правды о коде — Redis. Laravel не хранит код в БД, только проверяет.
- Удаление ключа после успешной проверки — хорошая практика: код одноразовый.
- В Laravel нужен Redis-клиент (например `predis/predis` или `phpredis`), подключение к тому же Redis, что и у Go. Ключи и TTL должны быть согласованы с Go (тот же префикс и время жизни).

**Что лучше, что хуже:**
- Хранить код в Redis в открытом виде для короткого TTL — нормально, Redis внутренний. Если нужен аудит «кто когда ввёл код», можно дополнительно логировать факт успешной верификации в БД/логах, не храня сам код.

## 5. Шаг 4: Resend (повторная отправка кода)

### Варианты

**Вариант A — лимит по времени отправки**

- В Redis ключ `verification_sent_at:{user_id}` с TTL 60 секунд (1 минута).
- Перед тем как Laravel кладёт задачу в очередь, проверить: есть ключ → ответ «повторный код можно запросить через N секунд», в очередь не класть.
- Если ключа нет — положить задачу в очередь и в Laravel же установить `verification_sent_at:{user_id}` с TTL 60 (или это может делать Go после отправки письма — тогда нужен контракт «после отправки Go пишет sent_at»).

**Плюсы:** жёсткий лимит «не чаще раза в минуту».  
**Минусы:** чуть сложнее (два ключа в Redis: код и sent_at).

**Вариант B — разрешить resend всегда**

- Laravel всегда кладёт задачу в очередь. Go при получении генерирует новый код, перезаписывает `verification_code:{user_id}` в Redis, снова шлёт письмо.
- Лимит только по TTL кода (5 минут) — старый код перестаёт работать после новой отправки.

**Плюсы:** проще, один ключ.  
**Минусы:** пользователь может спамить «отправить код» и получать много писем; нужен лимит на уровне API (rate limit по IP/user_id).

**Рекомендация:** комбинировать: rate limit в Laravel (например 1 запрос в 60 сек на user_id) + в Go при новой задаче просто перезаписать код и отправить. Лимит «не чаще раз в N» решается в API, а не в двух ключах Redis.

## 6. Шаг 5: Шаблон письма (HTML, стили, картинки)

### Сейчас

HTML собирается в Laravel (blade, подстановка кода и URL картинок). Готовый HTML уходит в очередь.

### После переноса

Шаблон должен жить в Go, чтобы в очереди не было ни кода, ни HTML. Варианты:

- **Простой HTML в Go:** один шаблон (файл или константа) с плейсхолдером `{{.Code}}` и при необходимости `{{.FrontendURL}}`. Картинки — по абсолютным URL из конфига/env (как сейчас в Laravel).
- **Один и тот же дизайн:** скопировать разметку из текущего blade в Go-шаблон и подставлять код и URL. Тогда письмо выглядит так же.

**Почему лучше в Go:** тогда Laravel вообще не участвует в формировании письма — только «инициировать отправку». Единая точка: генерация кода и содержимое письма в одном сервисе.

### Стили и «всё остальное» — как в Go

- Тело письма — это одна строка HTML. Стили в письмах обычно **инлайн** (`style="..."`) или в блоке `<style>`, потому что многие клиенты не подгружают внешний CSS. Картинки — по URL (`<img src="{{.ImageURL}}">`).
- В Go письмо не «рендерят» как Blade, а **собирают строку** из шаблона: берёшь тот же HTML/CSS из `verification.blade.php`, переносишь в файл шаблона в Go (например `verification.gohtml`). Вместо `{{ $code }}` — плейсхолдеры `{{.Code}}`, `{{.FrontendURL}}` и т.д.
- Пакет **`html/template`** (стандартная библиотека) подставляет значения в HTML и возвращает готовую строку; её и отправляешь в SMTP. Стили, разметка и картинки остаются теми же — меняется только место шаблона (Laravel → Go) и синтаксис подстановки (Blade → `{{.Field}}`).

## 7. Итоговая таблица ответственности

| Компонент | Действие |
|-----------|----------|
| **Laravel** | При запросе кода: не генерировать код, не писать в БД. Отправить в очередь только `email`, `user_id`, `type`. При проверке кода: прочитать из Redis `verification_code:{user_id}`, сравнить с вводом, при успехе — верифицировать email и удалить ключ. Resend ограничить rate limit (например 1 раз в 60 сек). |
| **Go** | Из очереди взять `email`, `user_id`, `type` → сгенерировать код → записать в Redis `verification_code:{user_id}` с TTL 5 мин → отрендерить письмо по шаблону → отправить по SMTP. |
| **Redis** | Общий для Laravel и Go. Ключ `verification_code:{user_id}` — код, TTL 300 сек. Опционально `verification_sent_at:{user_id}` для лимита resend, если не делаешь только rate limit в API. |

## 8. Чеклист внедрения

**Laravel**
- [ ] Убрать вызов `generateVerificationCode()` и запись в `users` при отправке кода.
- [ ] Публикатор шлёт в очередь только `email`, `user_id`, `type`.
- [ ] Подключить Redis; при проверке кода читать из Redis и сравнивать; после успеха удалять ключ.
- [ ] Rate limit на эндпоинты «send/resend code» (по user_id или IP).

**Go**
- [ ] Парсить новое сообщение (без `code` и `html`).
- [ ] Генерация кода через `crypto/rand`, запись в Redis с TTL 5 мин.
- [ ] HTML-шаблон письма с подстановкой кода (и URL при необходимости).

**Письмо (шаблон в Go)**
- [ ] Скопировать HTML и стили из `resources/views/emails/verification.blade.php` в Go-шаблон (например `templates/verification.gohtml`).
- [ ] Заменить плейсхолдеры Blade на Go: `{{ $code }}` → `{{.Code}}`, URL картинок/фронта → `{{.FrontendURL}}` и т.д., значения брать из конфига/env в Go.
- [ ] Рендер через `html/template`: загрузить шаблон, выполнить с данными `{Code, FrontendURL, ...}`, получить HTML-строку и передать в SMTP.
- [ ] Проверить письмо в почтовом клиенте (Mailpit/реальная почта): код подставляется, стили и картинки отображаются как раньше.

**Общее**
- [ ] Один Redis для Laravel и Go, одинаковые имена ключей и TTL.

После этого «с твоей стороны» правильно: в очереди только идентификация пользователя и тип операции; код рождается и хранится в Go + Redis; основная БД не нагружается верификационными кодами.
